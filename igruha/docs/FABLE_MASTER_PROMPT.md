## 3. Блок 1 — EPIC 1: ядро персонажа

### 3.1. Исправить (ручные правки, сделанные вручную и частично потерянные)

Прочитай `Assets/_Project/Scenes/Sandbox.unity` напрямую, не полагайся на предположения — часть правок могла откатиться, потому что вносилась во время Play mode.

- **CapsuleCollider на Player**: должен плотно облегать модель Karlan (замеренные bounds модели: size ≈ 0.72 × 1.22 × 1.07, feetY ≈ -0.18; заданы были radius 0.36, height 1.22). Проверь фактические значения, приведи к корректным. Дочерний `Karlan@Fast Run` должен стоять ступнями на нижней точке капсулы.
- **Позиция спавна не должна пересекаться с полом.** Был баг: капсула спавнилась внутри Plane, PhysX выдавал push-out с горизонтальной компонентой в геометрически неоднозначной точке (0,0) на triangulation seam примитива Plane → вечный дрейф по Z. `Rigidbody.linearDamping` держи ненулевым (0.05) — это защита от накопления микроимпульсов при толчках между игроками.
- **Cinemachine Camera (3.x, Third Person Follow + Rotation Composer)**: настроена «на глаз», требует пересмотра. Нужен нормальный party-game ракурс — персонаж по центру кадра, камера сзади-сверху, `Camera Side = 0` (строго за спиной, не сбоку), адекватные Camera Distance / Vertical Arm Length / Damping. Вынеси параметры так, чтобы их можно было переиспользовать в мини-играх (см. 4.4).

### 3.2. Доделать (не начато)

- **1.7 `ApplyPush(Vector3 direction, float force)`** — impulse-толчок другому персонажу. Публичная точка входа (будущий server-authoritative вызов), сила и радиус — сериализуемые параметры, без магических чисел.
- **1.8 «Смешное падение»** — при сильном импульсе или потере опоры проигрывается короткий клип (кувырок/падение), затем возврат в Idle. Не ragdoll. Порог срабатывания — параметр.
- **1.9 Респаун** — упал за границы арены / в дыру → возврат в точку старта. Точка старта — ссылка/сериализуемое поле, не хардкод. Должно переиспользоваться всеми мини-играми (см. 4.2).

### 3.3. ЕДИНЫЙ ШАБЛОН ПЕРСОНАЖА (важно — Karlan НЕ считать готовым)

Karlan сейчас в промежуточном состоянии, а не завершён. Задача — довести его до состояния **эталонного шаблона персонажа**, по которому потом за минуты подключаются остальные три.

**Принцип баланса — все персонажи функционально идентичны:**

- Одинаковая скорость бега, сила прыжка, гравитация, масса, сила толчка, инерция, скорость поворота, пороги падения. **Никаких персонажей-имбалансов** — это party-game, различие должно быть только визуальным.
- Отличаются между персонажами **только два параметра**: (1) габариты коллайдера/хитбокса под конкретную модель, (2) набор анимаций.
- Следовательно: все геймплейные значения выноси в **один общий конфиг** (ScriptableObject `CharacterConfig` или аналог), общий для всех персонажей. Индивидуально на персонажа остаются только: размеры капсулы + ссылка на Animator Controller / набор клипов.

**Тюнинг game feel — на твоё усмотрение, это твоя зона ответственности:**

Текущие значения (moveSpeed 5, jumpImpulse 5, дефолтная гравитация) выставлены наугад при первичной настройке и, скорее всего, не дают нужного ощущения. Подбери значения сам, исходя из общего вайба игры: тяжёлые, слегка неуклюжие, комично инерционные «ожившие игрушки» — референсы Gang Beasts, Party Animals, Pummel Party, Mecha Chameleon. Движение не должно быть картонным и плоским: нужен вес, инерция при разгоне/торможении, ощутимая дуга прыжка, читаемая реакция на толчки.

Конкретно пересмотри и обоснуй в резюме: скорость бега, ускорение/торможение, силу и высоту прыжка, множитель гравитации (стандартные −9.81 для аркадного party-game обычно слишком «плавучие» — рассмотри усиленную гравитацию с более резким падением), массу Rigidbody, linear/angular damping, силу impulse-толчка, порог срабатывания «смешного падения», скорость поворота.

Не спрашивай значения у пользователя — подбери сам, объясни логику выбора и сделай все параметры сериализуемыми, чтобы их можно было докрутить в редакторе после плейтеста.

**Требование к шаблону:** подключение нового персонажа (модель + анимации от Mixamo) должно сводиться к: создать prefab-вариант, подставить модель, задать размеры капсулы, назначить Animator Controller. Ноль строк нового кода.

## 4. Блок 2 — УНИВЕРСАЛЬНЫЙ ШАБЛОН МИНИ-ИГРЫ (главная задача)

Шаблон состоит из двух частей: **код-фундамент** (4.1–4.5) и **шаблон сцены/арены** (4.6). Обе части обязательны.

### 4.1. Общие механики (то, что переиспользуют большинство из 15 игр)

Реализуй как переиспользуемые системы в `Igruha.Core`, НЕ внутри Duck Hunt. Каждая должна подключаться к новой мини-игре без правки её кода.

| Бег / прыжок / поворот | все игры (уже есть в PlayerController — переиспользуй) |
| Impulse-толчок между игроками | Duck Hunt, Прятки, Экзамен, тай-брейк, Дырка в стене |
| Удар / knockback от попадания | Duck Hunt, Камеры-ловушки, тай-брейк |
| Смешное падение + вставание | почти все |
| Выбывание / временная «смерть» + респаун | Duck Hunt, Рейс на память, Экзамен, Плачущие ангелы |
| Подбор предмета и бросок | Переноска предмета, Duck Hunt, тай-брейк (подушка) |
| Стрельба (прицел + отдача) | Duck Hunt |
| Кнопки/триггеры активации ловушек | Duck Hunt, Камеры-ловушки, Рейс на память |

| Определение мест и очков | все |

Проектируй интерфейсами/компонентами: `IPickupable`, `IDamageable` (или аналог под «попадание → кувырок»), `ITrapTrigger`, `IInteractable` — точные имена на твоё усмотрение, но принцип: мини-игра **композирует** готовые компоненты, а не пишет свои.

### 4.2. Границы арены, зоны падения, респавн

- Компонент зоны смерти/падения (`KillZone` или аналог): игрок попал → комичное падение → респавн в назначенной точке (или выбывание, если правила игры так требуют — режим настраивается).
- Система точек спавна на **2–8 игроков** с поддержкой ролей (охотник/утки, ведущий/толпа, команда A/команда B). Не хардкодь количество игроков нигде.

### 4.3. Таймер и автозавершение

Обязательное требование: **у каждой мини-игры есть лимит времени, по истечении которого она завершается автоматически** и результаты считаются по текущему состоянию. Реализуй как общую систему с настраиваемой длительностью на игру, с событием окончания, на которое подписывается мини-игра/SessionManager.

### 4.4. Камеры

- 3rd-person камера (Cinemachine, из 3.1) — переиспользуемый пресет для бегательных игр.
- Заложи возможность переключения режима камеры под тип игры (по GDD 9.2 нужны также top-down и fixed), но **реализуй сегодня только 3rd-person** — Duck Hunt и хаб используют её. Остальные режимы — заглушки/точки расширения, не полноценная реализация.

### 4.5. Обучающая заставка (как в Pummel Party)

Переиспользуемый UI-компонент, показываемый перед стартом любой мини-игры: название, цель, базовое управление. Данные конкретной игры приходят снаружи (ScriptableObject с полями: название, описание цели, список действий управления, длительность показа). Закрывается по таймеру или по вводу. Для каждой новой игры — только новый ScriptableObject, ноль нового кода.

### 4.6. ШАБЛОН СЦЕНЫ мини-игры (обязательно)

Собери сцену-заготовку `MinigameTemplate` (она уже создана пустой в EPIC 0) как реальный работающий шаблон, из которого копируется каждая новая арена:

- Корневой объект-менеджер с компонентом, реализующим `IMinigame`.
- Готовая иерархия-заготовка: `_Arena` (геометрия), `_Spawns` (точки спавна 2–8 + ролевые), `_Bounds` (KillZone/границы), `_Traps`, `_Pickups`, `_UI` (таймер/счёт/подсказки), `_Camera` (3rd-person пресет), `_Lighting`.

## 7. Блок 5 — DUCK HUNT (первая мини-игра на шаблоне)

Реализуй по схемам уровня из `docs/images/` (разрез башни по этажам + планировка отдельного этажа). Это вертикальный срез: он должен использовать **только** системы из шаблона (раздел 4) и добавлять поверх минимум уникального кода.

**Структура арены (по планировке):**

- **Башня из 5 этажей**, чередующиеся биомы: этаж 1 ферма → этаж 2 ферма → этаж 3 зима → этаж 4 ферма → этаж 5 зима (финиш на крыше). Точное распределение биомов уточни по планировке, важен принцип чередования.
- **Одна грань башни открытая** — она простреливается снаружи.
- **Шахта лифта / лестница снаружи**, вдоль неё перемещается **охотник** и ведёт огонь по открытой грани. Охотник двигается по вертикали, ловя уток на разных этажах.
- **Спавн уток — этаж 1**, финиш — крыша (этаж 5).
- **Внутри каждого этажа** — три функциональные полосы (по планировке этажа): **паркур** (платформы с разрывами) → **укрытия от пуль** → **ловушки и кнопки активации**. Между этажами — переходы (лестницы/подъёмы).

**Роли и правила:**

- **Охотник** (1 игрок): стрельба с «жидким» прицеливанием и отдачей, разворачивающей его самого (GDD 4.2). Использует систему стрельбы из шаблона.
- **Утки** (остальные): бегут наверх, от попадания **не выбывают навсегда** — комично кувыркаются (система 1.8) и встают заново с потерей времени. Могут мешать друг другу толчками (`ApplyPush` из 1.7).
- **Ловушки и кнопки**: утка жмёт кнопку → срабатывает ловушка против соперников (пружина, падающий предмет, тележка — минимум 2 типа для проверки шаблона, не все).
- **Условие конца**: все утки дошли до крыши / истёк таймер раунда → определение мест (порядок добравшихся; недобравшиеся — по достигнутой высоте). Охотник получает место по числу помешанных.
- **Тестируемость в одиночку**: дебаг-переключатель роли (охотник/утка), чтобы можно было проверить обе стороны без второго игрока и без сети.

**Ассеты:** аналогично хабу — стор/AI, при отсутствии — блокинг на примитивах с правильными габаритами. Механика важнее арта на этом этапе.

## 8. Правила работы (из CLAUDE.md)

- SOLID / DRY / KISS. Никаких магических чисел. `[SerializeField] private`. Кэш компонентов в `Awake`. Input System. Addressables для загрузки мини-игр. Физика только в `FixedUpdate`, ввод и визуал в `Update`. Без аллокаций в update-циклах.

## 9. Порядок и отчётность
